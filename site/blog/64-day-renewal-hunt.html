Hunting 90-day assumptions before 64-day certificates arrive

2026-10-12 · renewhunt v0.1.0

On 7 October 2026 Let's Encrypt announced 64-day certificates: staging from 14 October 2026, production from 10 February 2027, with 45-day certificates to follow. Their advice to operators was blunt: grep for hardcoded numbers like 83, 80 or 60 in cron jobs, wrapper scripts and runbooks. renewhunt is a small, read-only Go CLI that does that grep with context, and tells you which hits will actually break.

Why a plain grep is not enough

Two problems. First, grep -rn 80 on a config tree drowns you in ports, percentages and line widths. Second, the same number means different things: certbot renew --days 80 is "days before expiry", while a wrapper that renews when a cert is 80 days old is "days since issuance". renewhunt separates these cases and grades each one against a 64-day lifetime (and flags what gets tight at 45).

How the scanner works

The scan package walks the paths you give it (or .), skipping .git, node_modules, vendor, build output and similar. It only reads files that look like config or scripts: shell, YAML/TOML/JSON, HCL, systemd units and timers, crontabs, Dockerfiles/Makefiles, plus extension-less files whose name contains renew, acme or cert. Binary or non-UTF-8 files are skipped and counted; files are capped at 2 MiB. Comment lines (#, //) are ignored.

Each line is then checked in two passes:

  1. Structured patterns — regexes for renew_before_expiry = N, RENEW_DAYS=N, cert-manager renewBefore: Nh / Nd, --days N (and --days-until-expiry, --renew-before-expiry), certbot renew … --days N, and renewal_window = N.
  2. Bare Let's Encrypt numbers — 83, 80, 60, 30 as standalone numbers, but only on lines that also mention something like renew, certbot, acme, letsencrypt, tls, cert-manager, lego, caddy, traefik or fullchain. That context gate is what keeps listen 80 out of your report.

Overlapping hits on the same line are deduplicated, keeping the longer (more specific) match.

The grading rules

For "days before expiry" values the thresholds are taken straight from the code:

WindowSeverityWhy
≥ 64 daysBLOCKEDA 64-day cert never has that much life left; the condition is always true or never meaningful.
45–63RISKYRenews almost immediately on 64-day; breaks under 45-day.
31–44RISKYLarge absolute window; tight under 45-day.
14–30OKFits the ⅔ guidance (≈21 days before expiry on 64-day).
7–13INFOVerify against your CA's lifetime.
< 7RISKYThin safety margin.

cert-manager renewBefore in hours is converted to days: ≥60 days BLOCKED, ≥45 RISKY, >21 RISKY (absolute window), otherwise OK. Bare day-since-issuance numbers: 83 and 80 are BLOCKED (past a 64-day expiry), 60 is RISKY (~4 days margin), 30 is INFO. renewBeforePercentage is deliberately not flagged — a percentage scales with the lifetime, which is exactly what you want.

Running it on the fixtures

The repository ships a fixture corpus in testdata/, also used by CI. This is real output from v0.1.0 (paths shortened, reasons cut):

$ renewhunt scan ./testdata
SCAN  files=8 skipped=0 findings=7 worst=BLOCKED
BLOCKED  bad/cron-certbot-days80:2          certbot renew --days 80
BLOCKED  bad/renew-script.sh:3              RENEW_DAYS=83
RISKY    bad/renew-script.sh:8              renew_before_expiry=60
BLOCKED  bad/wrapper.conf:2                 renew-before-expiry = 80
RISKY    cert-manager/certificate-720h.yaml:13        renewBefore: 720h
BLOCKED  cert-manager/certificate-90d-window.yaml:13  renewBefore: 2160h
OK       good/renew-21d.yaml:2              renewBefore: 504h
$ echo $?
1

The exit code is 1 whenever any finding is BLOCKED, 2 on usage errors, 0 otherwise — so renewhunt scan ./deploy works as a CI gate as-is, and -json gives you machine-readable findings with path, line, column, match, severity, reason and hint.

Clients and timers

Running renewhunt with no subcommand also probes ACME clients on PATH (certbot --version, acme.sh, lego, and cert-manager via kubectl) and adds notes — e.g. certbot below 4.1 gets a suggestion to upgrade for ARI (ACME Renewal Information). It then lists systemd timers and cron lines that mention certbot/acme/letsencrypt, so you can see when renewal actually runs. -system extends the scan to /etc/letsencrypt, /etc/cron.*, systemd unit dirs, /root/.acme.sh and /home.

What it does not do

renewhunt never renews certificates, never edits files and makes no network calls during a scan. It does not check live endpoints (see certfan for multi-IP TLS consistency). A live expiry probe and a cert-manager renewBeforePercentage suggestion are planned for v0.2; an ARI endpoint probe for v0.3 (ROADMAP).

Try it

go install github.com/Blackman99/renewhunt/cmd/renewhunt@latest
renewhunt scan /path/to/your/infra-repo

False positive or missed pattern? Open an issue with the line — it becomes a fixture in testdata/.
